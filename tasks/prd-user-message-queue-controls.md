# PRD: 运行中用户消息队列控制

## Status

- 状态：待办，尚未实施
- 范围：Web Chat、Code 对话及 Gateway Run 消息队列
- 本文仅记录需求，不包含代码、数据库迁移或接口实现

## Background

当 Agent 正在执行长任务或连续调用工具时，用户仍需要追加新意图。当前交互不应只提供单一的“等待当前任务结束后执行”语义，而应允许用户明确选择消息如何进入正在运行的任务，并能查看和调整尚未执行的消息顺序。

## Goals

- 同一个运行中的 Session 可以保存多条待处理用户消息。
- 每条消息具有明确的队列事件类型，前后端使用一致的执行语义。
- 用户可以置顶或重新排序尚未注入上下文的消息。
- 需要立即影响当前任务的消息，可以在最近一次安全注入点进入 LLM 上下文。
- 页面清楚展示消息状态，避免用户误以为消息已经被模型读取。

## Queue Event Types

### 1. 尾部排队（enqueue）

- 新消息追加到队列末尾。
- 支持连续提交多条消息，默认按 FIFO 顺序执行。
- 当前 Run 结束或进入约定的后续执行点时，按顺序取出消息。

### 2. 置顶（pin）

- 新消息插入所有普通待处理消息之前。
- 多条置顶消息之间的顺序需要有确定规则，建议默认按置顶时间 FIFO，避免后置顶消息无限抢占。
- 已经注入 LLM 上下文或正在执行的消息不能再置顶。

### 3. 立即加入上下文（steer）

- 消息不等待当前 Run 完整结束，而是在最近一次安全边界注入 LLM 上下文。
- 安全边界建议定义为：当前工具调用结束、下一次请求 LLM 之前。
- 不应强行中断正在执行且不可安全取消的工具；如用户同时要求停止，应走独立的 Run Cancel 流程。
- 注入成功后必须产生可观察事件，前端将消息状态从“等待注入”更新为“已进入上下文”。

### 4. 重新排序（reorder）

- 用户可以调整尚未执行、尚未注入上下文的消息顺序。
- 重排操作应基于队列版本或乐观锁，避免多个浏览器同时修改造成静默覆盖。
- 服务端是最终顺序的唯一来源，成功后返回完整的规范化队列快照。

## Functional Requirements

- [ ] 队列项至少包含 `id`、`session_id`、`run_id`、`content`、`event_type`、`position`、`status`、`created_at` 和创建账号。
- [ ] `event_type` 至少支持 `enqueue`、`pin`、`steer`；`reorder` 作为队列操作事件记录审计日志。
- [ ] `status` 至少区分 `pending`、`injecting`、`injected`、`executing`、`completed`、`cancelled` 和 `dropped`。
- [ ] 同一 Session 的多条普通消息按照稳定 FIFO 顺序处理。
- [ ] 置顶只影响尚未处理的队列项，不改变已经进入上下文的历史。
- [ ] 工具执行完成钩子检查待注入的 `steer` 消息，并在下一次 LLM 请求前加入上下文。
- [ ] 用户能够查看队列、提交不同类型的消息、置顶现有消息、拖动或按钮重排、删除尚未处理的消息。
- [ ] Chat 与 Code 页面分别操作各自 Session 的队列，不能跨 Session 或跨账号读取、排序、删除消息。
- [ ] 页面切换、刷新或更换浏览器后，从服务端恢复队列及每条消息的最新状态。
- [ ] Run 被停止时，不再接受新队列消息；已有 pending 消息采用统一策略处理并明确标记，不能静默丢失。
- [ ] 所有写操作支持幂等请求，重复提交、重试或 SSE 重连不能产生重复消息。
- [ ] 队列新增、注入、重排、删除和丢弃均写入审计事件，并通过 SSE 推送状态变化。

## UX Requirements

- [ ] 发送消息时提供执行方式选择：排队、置顶、立即加入上下文。
- [ ] 默认使用“排队”，避免普通发送意外改变当前任务方向。
- [ ] 待处理区域显示当前规范顺序、事件类型和状态。
- [ ] 只有 pending 项允许重排或删除；其他状态的控件禁用并说明原因。
- [ ] “立即加入上下文”需要明确表达它会改变正在进行的任务，但不会自动停止当前工具。
- [ ] 服务端拒绝并发重排时，前端刷新队列并提示用户重新操作。

## Suggested API Surface

以下仅作为后续设计输入，实施前仍需结合现有 Gateway 路由确认：

- `GET /v1/agent/runs/:runId/messages/queue`：获取规范化队列。
- `POST /v1/agent/runs/:runId/messages/queue`：提交消息及事件类型。
- `POST /v1/agent/runs/:runId/messages/:messageId/pin`：置顶现有 pending 消息。
- `PUT /v1/agent/runs/:runId/messages/queue/order`：按消息 ID 列表重排，携带队列版本。
- `DELETE /v1/agent/runs/:runId/messages/:messageId`：取消尚未处理的消息。

## Acceptance Scenarios

- [ ] 连续排队 A、B、C，服务端与页面均稳定显示并按 A、B、C 执行。
- [ ] A、B 已排队后置顶 C，执行顺序变为 C、A、B。
- [ ] 工具运行期间发送 steer 消息，工具结束后、下一次 LLM 请求前能够在上下文中读取该消息。
- [ ] 将 A、B、C 重排为 B、C、A，刷新页面和更换浏览器后顺序保持一致。
- [ ] 两个浏览器同时重排，旧版本请求被拒绝，不会覆盖较新的队列。
- [ ] 其他账号无法读取或修改该 Run 的任何队列项。
- [ ] 停止 Run 后提交新消息会得到明确错误，原 pending 消息均有最终状态。
- [ ] SSE 断开重连后不会重复展示或重复执行任何队列项。

## Non-Goals

- 本待办不实现跨 Session 的全局任务调度。
- 本待办不允许修改已经持久化的历史对话顺序。
- 本待办不把“立即加入上下文”等同于强制中断当前工具。
- 本待办不定义多 Agent 或多 Worktree 之间的任务依赖调度。

## Open Questions

- 多条置顶消息采用 FIFO，还是允许用户选择“插入队首”导致 LIFO？建议 FIFO。
- Run 正常结束后剩余 pending 消息应自动启动新 Run，还是等待用户确认？
- Run 被取消时，pending 消息应标记为 dropped，还是迁移到 Session 的下一次 Run？
- steer 消息是否允许附带文件、图片等复合内容，还是第一阶段仅支持文本？
- 队列是否需要持久化到数据库以支持 Gateway 重启恢复？从跨浏览器恢复需求看，建议持久化。
